# Direct3D 12 backend design

Status: **phases 0-5 core paths done, in progress overall** — the device layer
covers adapter enumeration, the debug layer, a WARP fallback, a fence-synchronized
direct queue, committed buffers, 2D color and depth textures, descriptor heaps
with CBV/SRV/UAV, sampler, RTV and DSV views, resource transitions and copies.
Three paths are end-to-end on hardware and WARP: compute (HLSL -> DXIL -> root
signature -> PSO -> dispatch -> UAV readback), render (root constants, static
samplers, SRV descriptor tables, input layouts with vertex buffers, depth
testing, multiple render targets, RTV/DSV clear + draw + pixel readback), and
swapchain/present (flip-model DXGI swapchain, frame-latency pacing, back-buffer
readback, present and resize). Shaders can be authored in WGSL: naga `hlsl-out`
produces HLSL and DXC compiles it to DXIL. WGSL resources in `@group(0)` map onto
HLSL registers by binding index (uniform buffers to `bN`/root constants,
textures to `tN`); sampler bindings still need the sampler-heap model of the
`naga` HLSL backend. Ray tracing (DXR) works through bottom/top-level acceleration structures, inline
ray queries and DXR 1.1 ray-tracing pipelines (state objects, shader binding
table, `DispatchRays`); external memory/shared handles are still open.
acceleration structures and inline ray queries; ray-tracing pipelines are not
implemented yet. 
Root signatures and pipeline states are cached, and device loss is
detected and surfaced as a dedicated error. Automatic resource recreation,
acceleration structures and the HAL traits/backend selection are still open.

Related: [motivation.md](motivation.md), [FAQ.md](FAQ.md),
[synchronization.md](../../docs/synchronization.md).

## Scope

Direct3D 12 is the Windows low-level graphics API. It sits at the same level as
Vulkan and Metal, i.e. it maps onto the `blade-graphics` HAL and not onto the
scene layer:

```
blade-render / blade-engine        3D rendering, UI composition
        ^
blade-graphics (HAL traits)        <- d3d12 | vulkan | metal | gles
        ^
D3D12 | Vulkan | Metal             native low-level APIs
```

**D2D is not a higher level of D3D.** Direct2D is a 2D vector/text drawing API
layered on D3D11 + DXGI; it is not an encapsulation of D3D12. A 2D API belongs
above the HAL (the role egui plays today via `blade-egui`) and cannot consume a
D3D12 device directly — D2D/D3D12 interop requires a separate D3D11 device and
DXGI shared surfaces, which is out of scope for this backend.

## Goals

- Feature parity with the Vulkan backend for the parts Blade actually uses:
  compute, render, transfer, dynamic rendering, GPU-driven draws, ray tracing.
- Keep the synchronous-by-default command model: record into command lists on
  the calling thread, submit in buckets from the engine layer.
- No `wgpu-hal` style state tracking; the user pushes bindings explicitly.
- Prefer modern DXGI / D3D12 features over compatibility paths (Blade targets
  mid/high-end hardware and fresh drivers).

## Non-goals (initially)

- D3D11 / D3D10 / D3D9 backends.
- Feature levels below 12_0. Blade's Vulkan backend already requires 1.3-era
  features (dynamic rendering, descriptor indexing, ray queries), and D3D12
  only reached parity with those at feature level 12_0 + recent OS builds.
- Direct2D, DirectWrite, DirectComposition.
- Xbox-specific extensions (GDK), UWP/AppContainer swapchain variants.

## Dependency and shader toolchain

- COM bindings: the `windows` crate (MIT/Apache-2.0), enabled by the `d3d12`
  cargo feature. Only needed on `cfg(windows)`, so other targets never link it.
- Shaders: `naga` already lives in `blade-graphics` (see the workspace `naga`
  fork). D3D12 consumes **DXIL**, which `naga` does not emit today, so the path
  is WGSL -> HLSL (naga `hlsl-out`, `src/d3d12/wgsl.rs`) -> DXIL
  (`src/d3d12/shader.rs`, `ShaderCompiler` loads `dxcompiler.dll` at runtime via
  `BLADE_DXC_PATH` or the DLL search path and calls `IDxcCompiler3::Compile`;
  failures carry the DXC diagnostics). Resource bindings in generated HLSL need
  a naga binding map, which arrives with the HAL binding model.
  - Phase plan A: `naga` WGSL input -> `naga` `hlsl-out` -> compile HLSL to DXIL
    at runtime with `dxcompiler.dll` (`IDxcCompiler3`), producing a pipeline
    cache keyed by (source hash, entry point, defines, feature level).
  - Phase plan B (later): offline DXIL via build scripts, or a custom
    `naga` `dxil-out` backend. Until then `dxcompiler.dll` is a runtime
    dependency, which is also how most D3D12 engines ship.
- DXIL signing (`dxil.dll`) is optional for development, required for
  production distribution; load it next to `dxcompiler.dll`.
- `windows` crate features are kept minimal: `Win32_Foundation`,
  `Win32_Graphics_Direct3D`, `Win32_Graphics_Direct3D12`,
  `Win32_Graphics_Dxgi`, `Win32_Graphics_Dxgi_Common`. Add more per phase.

## Blade HAL -> D3D12 mapping

| Blade HAL concept | D3D12 equivalent |
|---|---|
| `Instance` | `IDXGIFactory6` + adapter enumeration |
| `PhysicalDevice` / `Adapter` | `IDXGIAdapter1` + `D3D12_FEATURE_DATA_*` queries |
| `Device` | `ID3D12Device` (one per adapter, node mask for multi-adapter later) |
| `Queue` | `ID3D12CommandQueue` (direct / compute / copy) |
| `CommandEncoder` | `ID3D12GraphicsCommandList` + per-frame `ID3D12CommandAllocator` |
| `CommandBuffer` | recorded command list, submitted as a unit |
| `DescriptorSet` | range in a shader-visible descriptor heap |
| `PipelineLayout` | `ID3D12RootSignature` (32-bit root constants for push data) |
| `Shader` | DXIL blob + reflection from `naga` |
| `RenderPipeline` / `ComputePipeline` | `ID3D12PipelineState` (PSO) |
| `Buffer` / `Texture` | `ID3D12Resource` (committed or placed in `ID3D12Heap`) |
| `Sampler` | descriptor heap entry + static sampler in root signature |
| `Semaphore` / `Fence` | `ID3D12Fence` + `HANDLE` events |
| render pass | no pass objects: `OMSetRenderTargets` + resource barriers |
| `Format` | `DXGI_FORMAT` |
| `Extent` / `View` | `D3D12_VIEWPORT` / `D3D12_RECT` |
| `blade-graphics` surface | `IDXGISwapChain4` (flip model) wrapping an `HWND` |
| acceleration structures | `ID3D12Resource` BLAS/TLAS (DXR 1.1) |
| ray query in shaders | `RayQuery<RAY_FLAG_NONE>` (DXR 1.1, SM 6.5) |
| external memory | `ID3D12Heap` sharing / Win32 handle import-export |

Blade's push-constant-ish "plain data" maps to root constants (Blade limits
`PLAIN_DATA_SIZE` to 256 bytes, which fits the 32 root-constant limit nicely).
Blade's "bindings are re-pushed after every pipeline change" maps well to
descriptor-heap copies: a pipeline change invalidates the root signature, so
descriptor ranges are rewritten per draw, matching Vulkan's push-descriptor
model.

## Memory and residency

- One `ID3D12Heap` per Blade memory type, resources placed into heaps; this
  mirrors Vulkan's `gpu-alloc` sub-allocation and makes external memory
  (imported/exported heaps) natural.
- D3D12 requires explicit residency management. For desktop-only targets keep
  every resource resident (`MakeResident`) and treat eviction as out of scope;
  memory pressure is handled by the existing `blade-render` budgets.
- Upload/readback use the existing memory types (`Upload`, `Download`,
  `Shared`, `DeviceTransient`) with the same sub-allocation scheme as Vulkan.
- UAV/descriptor heaps are shader-visible, separate CBV/SRV/UAV and sampler
  heaps, sized from Blade's `RESOURCES_IN_GROUP` and per-stage limits.

## Command model

- Each recorded command buffer owns a `ID3D12GraphicsCommandList` and an
  allocator; reset happens only after the submission fence for that allocator
  has passed.
- Barriers are explicit: Blade's catch-all barrier maps to
  `ResourceBarrier` transitions between `D3D12_RESOURCE_STATES`; the engine
  layer already decides the source/destination states.
- Dynamic rendering: no render passes, `OMSetRenderTargets` +
  `ClearRenderTargetView`/`ClearDepthStencilView` and `BeginRenderPass`-less
  draws. This matches Blade's Vulkan dynamic-rendering path one-to-one.
- Multi-queue: start with a single DIRECT queue; later split into
  direct/compute/copy with the same semaphore model as Vulkan.

## Synchronization and presentation

- `ID3D12Fence` values per queue replace Vulkan timelines/semaphores.
- Swapchain: `IDXGISwapChain4` with `DXGI_SWAP_EFFECT_FLIP_DISCARD`,
  3 buffers, `DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT` for pacing.
- `Present` returns `DXGI_STATUS_OCCLUDED` / `DXGI_ERROR_DEVICE_REMOVED`; the
  surface code must handle device-lost and recreate all objects (Vulkan path
  already has the equivalent handling).

## Ray tracing

- DXR 1.1: `ID3D12Device5::CreateStateObject` for ray-tracing pipelines,
  `ID3D12GraphicsCommandList4::BuildRaytracingAccelerationStructure` for
  BLAS/TLAS, and inline `RayQuery` for ray queries (Blade's existing
  acceleration-structure API maps directly).
- Same transform convention as the Metal/Vulkan paths
  (`AccelerationStructureTransform`), with D3D12 requiring row-major 3x4.

## External memory / interop

- `ExternalMemorySource::Win32(Some(handle))` already exists in
  `blade-graphics/src/lib.rs` for the Vulkan backend. D3D12 will import
  `D3D12_HEAP` NT handles and `ID3D12Resource` shared handles, and export the
  same, enabling D3D12 <-> Vulkan interop on Windows.
- External memory is a phase 4+ item; the phase 0 probe does not touch it.

## Debugging and validation

- `D3D12GetDebugInterface` + `ID3D12Debug::EnableDebugLayer` behind
  `BLADE_D3D12_DEBUG=1`.
- GPU-based validation and DRED behind `BLADE_D3D12_DEBUG_GPU=1`.
- PIX markers map to `PIXBeginEvent`/`PIXEndEvent` (via
  `ID3D12GraphicsCommandList::BeginEvent`), matching the existing
  `profiling`/trace scopes.
- `renderdoc` already exists as a dev-dependency for Windows/Linux.

## Testing

- `cargo check --target x86_64-pc-windows-msvc` on every change to catch
  Windows-only regressions (macOS/Linux hosts can cross-check).
- Phase 1+: headless tests on the WARP software adapter, then the same
  reference-image tests (`tests/gpu_examples.rs`) as Vulkan/Metal.
- Device-lost, resize, and multi-frame present paths get dedicated tests in
  phase 5.

## Risks and open questions

1. **DXIL toolchain**: `naga` HLSL output quality varies per construct; the
   long-term clean solution is a `naga` `dxil-out` backend (upstream work).
   Short term we depend on `dxcompiler.dll`/`dxil.dll` at runtime.
2. **Feature level**: blade's Vulkan requirements effectively need D3D12
   feature level 12_0 plus SM 6.0+; ray queries need SM 6.5 (Windows 10 1903+
   drivers). Older hardware stays Vulkan-only.
3. **Descriptor management**: Blade re-pushes bindings per draw, which is
   expensive with descriptor heaps. Vulkan solves this with push descriptors +
   templates; D3D12 has no push descriptors, so phase 2 needs a descriptor
   ring allocator per frame (same shape as `wgpu-hal`'s dx12 allocator).
4. **Residency**: desktop-only residency tracking is fine for now, but if
   external memory/texture streaming arrives, eviction must be implemented.
5. **Multi-adapter / linked GPUs**: out of scope; node mask fixed to `1`.
6. **`windows` crate churn**: API naming changes between releases; pin the
   minor version.

## Implemented device layer (phases 0-1)

`blade-graphics/src/d3d12/mod.rs` exposes:

- `AdapterInfo` — name, vendor/device id, dedicated and shared memory, software
  flag, with a `Display` impl for logging.
- `enumerate_adapters()` — hardware adapters in GPU-preference order, including
  WARP when DXGI lists it.
- `InitOptions` — adapter preference, `force_warp`, `warp_fallback`, and
  `enable_debug_layer` (defaults from `BLADE_D3D12_DEBUG`); `headless()` selects
  WARP for CI.
- `init()` / `init_with_options()` — create the factory, the `ID3D12Device` at
  feature level 12_0, a direct `ID3D12CommandQueue`, an `ID3D12Fence` with a
  waitable event, and (for WARP) the enumerated software adapter.
- `Device` — `create_buffer`, `record`, `submit`, `wait`, `wait_idle`, plus
  `raw()`/`queue()` accessors used by later phases.
- `Buffer` — committed `ID3D12Resource` in `Memory::Device`/`Upload`/`Readback`
  with CPU `write`/`read` for the staging heaps, state tracking, and
  `gpu_address()` for views.
- `CommandEncoder` — resource transitions (`ResourceState`), `copy_buffer`,
  buffer->texture and texture->buffer copies, submitted as one unit through
  `Device::submit`, which returns a `SyncPoint`.
- `Texture` / `TextureDesc` — 2D textures in device-local memory; `upload_texture`
  and `read_texture` are synchronous staging helpers that pack rows through the
  D3D12 copy footprints (`GetCopyableFootprints`), so mip 0 is verified
  byte-for-byte.
- `DescriptorHeap` / `DescriptorHeapType` / `DescriptorRange` — shader-visible
  CBV/SRV/UAV and sampler heaps with a bump allocator (`allocate`, `reset`,
  `remaining`) and CPU/GPU handle helpers.
- View creation on `Device` — `create_buffer_cbv`, `create_buffer_srv_typed`,
  `create_buffer_srv_structured`, `create_buffer_uav_typed`,
  `create_texture_srv`, `create_sampler`; `SamplerDesc` has a linear/clamp
  default. Buffers used with UAVs must be created through
  `BufferDesc::with_unordered_access()` — D3D12 removes the device on a UAV
  created from a resource without the flag, so the layer rejects it early.
- `format_size` — element sizes for the formats the layer knows about.
- `Device::check_device` — surfaces a removed device at the phase boundary where
  the bad resource use happened instead of at the next submission.
- `ShaderCompiler` (`src/d3d12/shader.rs`) — runtime DXC: loads
  `dxcompiler.dll` (`BLADE_DXC_PATH` override), creates `IDxcCompiler3` and
  compiles HLSL to DXIL; `Error::ShaderCompile` carries the compiler output.
- `RootSignature` / `RootDescriptorTable` / `DescriptorRangeKind` — serialized
  compute root signatures with one descriptor table per entry (no root
  constants or static samplers yet).
- `ComputePipeline` — `ID3D12PipelineState` built from DXIL plus its root
  signature; `Device::create_compute_pipeline`.
- Compute recording on `CommandEncoder` — `set_descriptor_heap`,
  `set_compute_pipeline`, `set_compute_descriptor_table`, `dispatch` and
  `uav_barrier`, which together with `transition_buffer`/`copy_buffer` cover a
  full dispatch-then-readback frame.
- Render targets: `DescriptorHeapType::Rtv` (CPU-only heap),
  `TextureDesc::with_render_target()` (sets the resource flag),
  `Device::create_render_target_view`, and `ResourceState::RenderTarget`.
- Graphics root signatures and pipelines: `RootParameter` (descriptor tables or
  32-bit root constants), `Device::create_graphics_root_signature`,
  `RenderPipeline` / `RenderPipelineDesc` and `Device::create_render_pipeline`
  (vertex + pixel DXIL, one color target, no input layout, no depth; rasterizer,
  blend and depth-stencil state are filled explicitly because D3D12 zeroed state
  is not valid default state).
- Render recording on `CommandEncoder` — `set_render_targets`,
  `clear_render_target`, `set_viewport`, `set_scissor`, `set_render_pipeline`,
  `set_graphics_root_constants`, `draw_instanced`: a full clear + fullscreen
  triangle + pixel-readback pass.
- Swapchain/present: `Device::create_swapchain` (HWND) and
  `create_swapchain_for_composition`, `Swapchain::acquire` / `texture` /
  `render_target` / `present` / `resize`. Two flip-discard buffers, maximum frame
  latency 2 and a frame-latency waitable object with bounded waits (a hidden or
  stalled presentation engine errors out instead of blocking). Present returns
  [`PresentStatus`] so `DXGI_STATUS_OCCLUDED` is not treated as a failure.
- WGSL bindings: globals in `@group(0)` are mapped onto HLSL registers with
  `register = binding index` in space 0 (`naga::back::hlsl::BindingMap`), which
  lines up with the descriptor tables and root constants this backend builds.
  Groups other than 0 are rejected with a clear error until register spaces are
  wired into the root signature. Sampler bindings are not supported yet: the
  workspace `naga` fork models samplers as a dynamically indexed heap (the
  `wgpu-hal` dx12 model), which does not match our static samplers.
- WGSL front end: `d3d12::wgsl` translates WGSL to HLSL with naga `hlsl-out`
  (`wgsl_to_hlsl`, entry-point selection, parse/validate diagnostics), and
  `ShaderCompiler::compile_wgsl` runs the whole WGSL -> HLSL -> DXIL path.
  `ShaderCompiler::translate_wgsl` exposes the generated HLSL for debugging.
- Ray-tracing pipelines (DXR 1.1): `RayTracingPipelineDesc` /
  `RayTracingPipeline` build a state object from a DXIL library
  (`ShaderCompiler::compile_hlsl_library`, `lib_6_3`) with a hit group, shader
  config, pipeline config and serialized global root signature
  (`Device::serialize_compute_root_signature`). `shader_identifier` yields the
  32-byte records, `Device::create_shader_binding_table` lays out
  ray-gen/miss/hit-group tables, and the encoder exposes
  `set_ray_tracing_pipeline` / `dispatch_rays`.
- Heaps and residency: `Heap` / `HeapType` create explicit `ID3D12Heap`s with a
  64 KiB-aligned bump allocator (`allocate`, `allocated`, `remaining`),
  `Device::create_placed_buffer` / `create_placed_texture` place resources at
  heap offsets (`texture_allocation_size` queries the required size/alignment),
  and `Device::make_resident` / `evict` manage residency. Placed resources queue,
  render and copy like committed ones, so they reuse the existing encoder API.
- Storage textures: `TextureDesc::with_unordered_access()`,
  `Device::create_texture_uav` (2D mip-0 UAV), `CommandEncoder::copy_texture`
  (whole mip 0) and `CommandEncoder::uav_barrier_texture`.
- Ray tracing: `AccelerationStructure` / `BlasGeometry` / `TlasInstance`,
  `Device::create_bottom_level_acceleration_structure` /
  `create_top_level_acceleration_structure` (DXR prebuild + synchronous build,
  result buffers created directly in the ray-tracing state),
  `Device::create_acceleration_structure_srv` for ray-query shaders,
  `ResourceState::AccelerationStructure` and `Device::raytracing_tier`.
  `Error::Unsupported` reports DXR-less adapters.
- Pipeline cache: root signatures are keyed by a hash of their serialized blob,
  compute/render pipeline states by a hash of shader bytecode, root-signature id,
  color formats, depth format and vertex attributes. Identical requests return
  the same object (`RootSignature::id`, `RenderPipeline::id`,
  `ComputePipeline::id`), `pipeline_cache_stats` exposes hits/misses and
  `clear_pipeline_cache` drops the entries.
- Device loss: `Device::is_lost` / `check_device`, `Error::DeviceLost(reason)`
  from `GetDeviceRemovedReason`, and device errors from `record`, `submit`,
  `wait`, buffer/texture creation are mapped to it. `Device::remove_device` uses
  the debug layer to simulate a lost device in tests; recovery is "create a new
  device plus the resources that were bound to the old one".
- Texture sampling: `StaticSampler` bakes clamp/linear samplers into the root
  signature (`create_graphics_root_signature_with_samplers`), and
  `CommandEncoder::set_graphics_descriptor_table` binds an SRV table for
  `Texture2D.Sample`.
- Multiple render targets: `RenderPipelineDesc::color_formats` accepts 1-8
  formats and `set_render_targets` / `set_render_targets_with_depth` take a slice
  of RTVs, matching `SV_Target0..N` in the pixel shader.
- Vertex input and depth: `VertexAttribute` + `RenderPipelineDesc::vertex_attributes`
  build the `D3D12_INPUT_ELEMENT_DESC` array, `depth_format` enables depth test
  (`LESS`) and writes; `DescriptorHeapType::Dsv`,
  `TextureDesc::with_depth_stencil()` and `Device::create_depth_stencil_view`
  add depth targets. Command recording gains `set_vertex_buffer`,
  `set_index_buffer`, `draw_indexed`, `set_render_targets_with_depth` and
  `clear_depth_stencil`; `ResourceState` gains `VertexBuffer`, `IndexBuffer`,
  `DepthWrite` and `DepthRead`.
- Diagnostics: `Device::debug_messages` (D3D12 info queue),
  `Device::dxgi_debug_messages` (DXGI info queue; needs the debug factory that
  `BLADE_D3D12_DEBUG=1` creates) and `Device::report_live_objects`.

Still missing for the HAL: automatic device-lost resource recreation, WGSL
sampler bindings and register spaces for multiple bind groups, WGSL ray queries,
multi-record SBT local data, a general sub-allocator, external memory and the
`hal` module wiring. A new allocator per encoder is
deliberate for now; the allocator ring arrives with the HAL command model.

## Verification

Windows only (the equivalents of `cargo test --features d3d12`):

```pwsh
# DXC release needed for the shader tests/examples; keep dxil.dll next to it.
$env:BLADE_DXC_PATH = "C:\path\to\dxc\bin\x64\dxcompiler.dll"

cargo test  -p blade-graphics --features d3d12 --lib d3d12
cargo run   -p blade-graphics --features d3d12 --example d3d12-probe
cargo run   -p blade-graphics --features d3d12 --example d3d12-smoke
cargo run   -p blade-graphics --features d3d12 --example d3d12-compile
cargo run   -p blade-graphics --features d3d12 --example d3d12-compute
cargo run   -p blade-graphics --features d3d12 --example d3d12-render
cargo run   -p blade-graphics --features d3d12 --example d3d12-swapchain
cargo run   -p blade-graphics --features d3d12 --example d3d12-mesh
cargo run   -p blade-graphics --features d3d12 --example d3d12-texture
cargo run   -p blade-graphics --features d3d12 --example d3d12-wgsl
cargo run   -p blade-graphics --features d3d12 --example d3d12-raytracing
# Visible window demo; needs an interactive desktop session.
cargo run   -p blade-graphics --features d3d12 --example d3d12-window
```

`d3d12-probe` lists adapters, initializes a hardware device and a WARP device.
`d3d12-smoke` copies 64 KiB through device-local memory, uploads and reads back a
2D texture, and creates buffer/texture/sampler descriptors on both adapters.
`d3d12-compile` compiles HLSL with DXC and checks that broken HLSL surfaces
diagnostics. `d3d12-compute` runs the whole compute path: HLSL -> DXIL -> root
signature -> PSO -> dispatch -> UAV barrier -> readback, verifying the output
values. `d3d12-render` runs the offscreen render path: graphics root signature
with root constants -> graphics PSO -> RTV clear to blue -> fullscreen green
triangle -> texture readback, verifying every pixel. `d3d12-swapchain` creates a
hidden window, renders into a flip-model swapchain, reads the back buffer back,
presents three frames, resizes and presents again; each adapter runs in its own
child process because DXGI does not always allow two swapchain/device stacks in
one process.

`d3d12-window` opens a real window, renders a procedural pattern into a
flip-model swapchain and presents 600 frames, so the backend can be watched on
an interactive desktop (the phase-0 reference screenshot shows the window with
the gradient/checker pattern).

`d3d12-raytracing` builds a triangle BLAS and a one-instance TLAS, runs a ray
query compute shader, then builds a DXR 1.1 ray-tracing pipeline
(state object + shader binding table), dispatches rays and checks both hit
distances (DXR tier 1.0/1.1; the reference GTX 1650 reports tier 0 and WARP
reports 1.1, so it runs on WARP).

`d3d12-wgsl` renders the fullscreen triangle with shaders written in WGSL,
showing the generated HLSL and verifying the DXIL output on both adapters, then
renders a WGSL textured quad whose uniform and texture bindings are mapped onto
`b0`/`t1` registers.

`d3d12-texture` uploads a procedural texture, samples it through an SRV table,
then has a compute shader write a storage texture through a UAV and copies it to
a second texture, verifying both; binds it through an SRV
descriptor table with a static sampler, draws a fullscreen quad and verifies
that every sampled texel matches the source.

`d3d12-mesh` compiles a mesh pipeline with `POSITION`/`COLOR` input attributes,
uploads vertex buffers, draws a near red and a far green fullscreen triangle
through a `D32_FLOAT` depth target and verifies that depth testing keeps the near
one on both adapters.

**Swapchain tests need an interactive desktop session.** Over SSH (session 0)
`CreateSwapChainForHwnd` fails with `DXGI_ERROR_NOT_CURRENTLY_AVAILABLE`; the
tests detect that and skip, and the composition swapchain path exists for such
environments. On a machine with a logged-in desktop, run the suite through Task
Scheduler (`schtasks /create /it ...`) to cover the real present path. Note that
`BLADE_D3D12_DEBUG=1` can make the swapchain example abort at process teardown in
remote sessions; the present path itself completes correctly. `BLADE_D3D12_DEBUG=1` enables the debug layer where the Windows
"Graphics Tools" feature is installed (it works on the reference machine).
